# StudyLens 评测说明

更新日期：2026-11-01。本文说明怎样测、怎样记分和怎样解释结果。项目流程的通俗讲解见 [项目流程讲解_非技术版.md](项目流程讲解_非技术版.md)。

## 1. 先区分三种结果

1. **程序测试**：人为制造正常和异常输入，检查流程有没有按规则工作。测试中可以用模拟模型；通过只能说明这段流程符合预期。
2. **检索评测**：真的在给定资料里搜索，检查必须找到的证据是否进入候选结果。它不等于最终答案正确率。
3. **真实问答评测**：实际调用配置的向量、重排和问答模型，再由人阅读答案、引用和标准要求打分。没有执行这一层时，回答准确率必须标记“未测”。

当前自建题集是合成的开发集，用来定位问题和防止回归；不代表真实用户分布，也不是独立盲测集。不能把测试替身产生的分数写成真实模型性能。

## 2. 两套题集不要混在一起计算

旧版 `evaluation/questions.csv` 有30题，资料来自三份示例笔记。参数为 `top_k=3`、最低匹配分数 `0.08`。已保存的2026-10-31基线：

- 单段问题：15/15命中。
- 多段问题：10/10找齐全部标注证据。
- 无答案问题：0/5返回空检索。

第三个结果说明词面相似不等于有答案，不能据此推断真实模型必然编造。旧版报告见 [基础修复与基线.md](基础修复与基线.md)。

新版 `evaluation/rag_cases.jsonl` 有18个独立场景，每题自带小资料集、标准依据和判断要求，包含术语、口语同义表达、参数、多资料、噪声、歧义、缺证、更新、删除、提示注入、冲突、闲聊、表格、层级和跨语言问题。其中12题预期正常回答；另6题用于检查拒答、澄清、删除或闲聊行为，不加入有答案题的召回分母。

新版题集使用原有TF-IDF检索时，在 `top_k=5`、最低匹配分数 `0.08` 下，证据召回与全部证据覆盖均为10/12，即83.33%。漏掉的两题是：

- R17：把“学过几天就想不起来”对应到“主动回忆”，词面匹配抓到了时间、教室等干扰资料。
- R18：中文问题查找英文助教答疑通知，基础字符检索没有找到目标英文证据。

这两题是新语义检索需要接受的检验，**尚不能据此宣称新系统已经提高了多少**。新的生产检索必须在同一题集、同一 `top_k` 下实际跑完后再比较。30题和18题的分数不能直接相减当作提升。

## 3. 每个指标到底算什么

**证据召回率 `evidence_recall_at_k`**：先对每道有答案题计算“找到了几条要求的证据 / 总共要求几条”，再平均。匹配同时检查资料编号和标注原文片段；不是只要提到相同关键词就算找到。失败题按0计入，不能删掉失败题来提高分数。

**全部证据覆盖 `all_evidence_coverage`**：只有该题要求的证据全部找到才得1，否则得0，再对12道有答案题平均。多来源问题只找到一半不会被算作完整覆盖。

**旧内容泄露 `forbidden_evidence_cases`**：更新或删除场景中，不应该再出现的内容是否仍被检索。目标是0，但这个题集通过不等于所有并发情形都已验收。

**自动行为正确率 `behavior_accuracy_auto`**：检查本来应该回答、拒答、澄清、闲聊时，程序实际选择了什么。接口故障不能冒充“正确拒答”。它只检查可观察行为，不能自动证明自然语言内容正确。

**答案关键词出现率 `answer_terms_presence_auto`**：用于快速发现明显漏项。答案即使出现所有关键词，也可能说错关系或数字，因此这个指标不能叫语义准确率。

**人工回答准确率 `manual.answer_accuracy`**：人工评分为1的数量 / 实际完成评分的数量。需要同时报告 `reviewed`、`model_cases`、`requested_cases` 和失败题数，不能只展示部分精选题的高分。

**人工引用支持率 `manual.citation_support_accuracy`**：在需要核对事实引用的已评分样本中，引用足以支持结论的比例。没有事实主张的正确拒答、澄清或闲聊可以填写 `N/A`，不会被当作“引用成功”凑分母；有事实回答或引用时必须填0或1。

召回指标在原问题上直接检索，与Agent动态改写后的效果分别记录。这样可以区分“检索器是否找到证据”和“Agent是否合理改写、使用证据”。每题记录还保留实际回答、引用、过程轨迹、用时和错误类别，方便分析失败原因。

## 4. 无费用基线怎么运行

在项目根目录、已安装项目依赖的Python环境中执行：

```powershell
python -B evaluate.py --output evaluation/generated/baseline30.csv --summary evaluation/generated/baseline30.json
python -B evaluate_rag.py --backend baseline --top-k 5 --output evaluation/generated/rag_baseline_new.json
```

这两条命令不调用真实模型。第一条复测30题；第二条在18题上运行原有TF-IDF检索。即使第二条文件名带有RAG，也不能把它解释为已经测试了Milvus、语义模型或Rerank。

结果中的 `answer_accuracy` 为 `null` 表示未测，不是0%，也不是100%。输出应放在 `evaluation/generated/` 或其他评测归档目录；不要覆盖题集和已保存的参考基线。

## 5. 真实生产检索和问答怎么运行

先按 [部署与运维.md](部署与运维.md) 建好服务，填写真实服务地址、模型和访问凭据。模型名称可以由服务商更新，运行时应记录实际使用的模型名、模型身份指纹、向量维度、分块配置指纹、题集指纹和 `top_k`。本轮脚本会保存这些信息；若服务商把模型名称当作动态别名，还需要自行记录控制台可获得的实际版本信息。

下面的命令在API容器里执行，因此能访问容器网络中的Milvus。输出放到可写、持久化的 `/app/var/evaluation/`。**这两条命令会产生真实外部模型费用，按需选择运行。**

仅验证生产检索，调用Embedding和Rerank，不请求问答答案：

```powershell
docker compose --env-file .env.rag -f deploy/compose.yml exec api python -B evaluate_rag.py --backend production --allow-paid --top-k 5 --output /app/var/evaluation/production_retrieval.json
```

进一步验证Agent和真实问答：

```powershell
docker compose --env-file .env.rag -f deploy/compose.yml exec api python -B evaluate_rag.py --backend production --allow-paid --with-model --top-k 5 --output /app/var/evaluation/production_answers.json
```

`--allow-paid` 是执行者明确选择调用付费Embedding/Rerank；`--with-model` 才进一步运行问答模型。运行这份交付时，未代替负责人执行这些付费命令。当前服务工厂要求完整部署配置，即使只做检索评测，也应先完成全部必要配置；有Key不代表相应模型账户一定有额度或权限。

评测为每次运行创建随机名称的独立Milvus集合和临时本地目录，每题再用不同的知识库编号。它不会往正式集合写入题集。结束后只清理经过“本次随机运行编号 + 实际模型指纹 + 维度”核对的集合；如果清理失败，报告中会保留实际集合名并返回失败状态，请维护者核对后处理，不能凭名称前缀批量删除。

缺少配置、服务不可达、某题执行失败或集合清理失败都会写入报告。启动失败时明确标记模型未运行，不能拿空报告计算准确率。如果进程被强制终止，也可能留下临时集合，需要维护者根据这次运行编号核对。

## 6. 怎样人工评分，而且不再次调用模型

真实问答完成后先保留原始JSON报告。导出与这份报告绑定的CSV模板：

```powershell
docker compose --env-file .env.rag -f deploy/compose.yml exec api python -B evaluate_rag.py --grade-existing /app/var/evaluation/production_answers.json --export-label-template /app/var/evaluation/manual_labels.csv
```

模板不会覆盖已有人工标签。将报告与模板复制出来阅读和填写：

```powershell
docker compose --env-file .env.rag -f deploy/compose.yml cp api:/app/var/evaluation/production_answers.json evaluation/generated/production_answers.json
docker compose --env-file .env.rag -f deploy/compose.yml cp api:/app/var/evaluation/manual_labels.csv evaluation/generated/manual_labels.csv
```

评分时按每题的 `rubric` 阅读原问题、输出和实际引用。不要只看答案是否流畅。

- `correct`：1表示回答满足该题要求且没有关键错误；0表示存在错误、缺关键结论、该拒答却编造、该回答却无故拒答，或者因服务故障未完成任务。
- `citations_supported`：1表示引用足以支持回答中的事实；0表示引用错位、缺必要依据或引用只说了另一件事。正确拒答、澄清和闲聊没有事实引用时填 `N/A`。
- `reviewer`：填写实际评分者姓名或稳定代号。
- `notes`：简短写明错在哪里，便于下一轮迭代。

不要改 `run_id`、`dataset_sha256`、`id` 和 `answer_sha256`；这些列把评分绑定到这一轮、这一份题集、这一份具体答案。标签与结果不匹配时脚本会拒绝汇总。它用于防止误用文件，不是防止人为篡改的数字签名。

可以分批评分：评分三列全空的题会暂时跳过并降低评分覆盖率；填写了一半的题必须补全。题号、运行编号或答案有变化，应重新导出新模板，不能复制旧分数。无真实问答结果的离线检索报告不允许导出此模板。

在本机离线汇总，不需要API密钥，也不会重跑模型：

```powershell
python -B evaluate_rag.py --grade-existing evaluation/generated/production_answers.json --manual-labels evaluation/generated/manual_labels.csv --output evaluation/generated/production_graded.json
```

原始报告和标签不会被评分输出覆盖。评分报告保留原文件和标签的指纹，方便追溯；全部未填时准确率仍为未测。报告中可能含评测资料和答案，真实业务资料的评测产物不要直接公开到GitHub。

## 7. 怎样形成可信的下一轮结论

先固定题集、标准依据、模型与检索参数，再比较基础检索与新检索。两轮都要保留成功题、失败题、费用、耗时和错误，不只选成功截图。参数调节应在开发集完成，然后另收集未参与调参的真实问题作为测试集。

特别关注四组结果：同义/跨语言证据是否更容易找到；引入多路召回后是否带来噪声；更新与删除后能否立刻使用当前资料；无答案或歧义问题是否正确停止或澄清。

目前可报告的是已保存的基础检索结果，以及各项程序回归测试的通过范围。真实Embedding、Rerank、问答质量、并发与费用需要后续实际服务验收；CI中使用确定性测试向量连接真实Milvus，只能证明数据库读写、过滤和版本流程，不能证明语义模型变得更准确。
