# StudyLens 工程版：部署与运维

日期：2026-11-01。先读 `项目流程讲解_非技术版.md` 理解业务，再按本文部署。本文提供命令和服务配置，不应当把“代码已经上传 GitHub”理解为外部 Milvus 与模型账户已经配置完毕。

## 1. 明确两个入口

`app.py` 是网页，使用 `requirements.txt`。当前 Streamlit Cloud 网页可以继续使用“临时笔记”。

`studylens.api` 是持久知识库服务，需要 `requirements-rag.txt`、Milvus、Embedding、Rerank 和问答模型。网页通过部署者设置的 `STUDYLENS_API_URL` 连接它。用户不能从页面把服务地址改成任意机器。

完整部署以单组织、一个知识库工作区、单 API 进程为边界。不同组织应使用不同部署、凭据与数据卷。当前版本不提供账户注册、逐用户配额或分布式锁。

## 2. 准备配置

在仓库根目录复制 `.env.rag.example` 为 `.env.rag`。该真实配置文件已经被 Git 忽略，不要使用 `git add -f`。

需要填写：

- `STUDYLENS_ADMIN_KEY`：管理凭据，能导入、替换、删除资料。
- `STUDYLENS_READER_KEY`：只读凭据，能问答、查看资料。必须与管理凭据不同，两者至少32字符，建议随机生成。
- `MILVUS_ROOT_PASSWORD`：首次初始化 Milvus 的密码；`MILVUS_TOKEN` 填 `root:同一密码`。生产可进一步使用权限更小的 Milvus 账户。
- `MINIO_ROOT_PASSWORD`：对象存储密码，独立设置；`MINIO_ROOT_USER` 默认 `studylens`。
- `EMBEDDING_API_KEY`、`RERANK_API_KEY`、`LLM_API_KEY`：分别负责向量、重排、回答；即使同一账户提供多个能力，也要确认对应模型可用。
- `EMBEDDING_DIMENSIONS`：必须与模型实际输出一致，默认 BGE-M3 的1024维。
- `RERANK_MIN_SCORE`：重排过滤阈值，默认0.25是待校准起点，不是正确率。
- `STUDYLENS_EMBEDDING_MAX_BATCHES`、`STUDYLENS_EMBEDDING_MAX_SECONDS`：一次完整导入的向量批次与阶段时间预算，默认16批、90秒。超过请拆分资料，不能盲目扩大配额。

默认服务商基址是 SiliconFlow 和 DeepSeek。模型名、额度和支持的请求协议应以服务商当前控制台为准。仅填写某个模型名称不会自动下载或开通它。

需要其他模型域名时，部署者把审核过的完整 HTTPS 基址加入 `STUDYLENS_ALLOWED_MODEL_BASE_URLS`（逗号分隔）。不接受 IP、端口、账号密码、查询串或重定向。新增域名也意味着信任该域名的运营者与解析配置，应从网络层限制出口。

## 3. 容器运行完整服务

需要已安装并运行 Docker Engine / Docker Desktop，以及 Compose V2。本任务不会自动安装 Docker 或购买云服务器。

仓库根目录执行：

```powershell
docker compose --env-file .env.rag -f deploy/compose.yml config --quiet
docker compose --env-file .env.rag -f deploy/compose.yml up -d --build
docker compose --env-file .env.rag -f deploy/compose.yml ps
```

`config --quiet` 只做校验，避免把配置中的秘密打印出来。首次会下载镜像、安装依赖和初始化数据库，需要等待。

访问 `http://localhost:8501`，选择“持久知识库”，填写管理凭据，点击“连接 / 刷新资料”。先导入一份允许发送给外部模型的短笔记。导入有真实 Embedding 费用；问答还会使用向量、重排和问答额度。

默认 API/网页只监听本机端口；Milvus、MinIO、etcd 没有公开宿主机端口。持久卷分别保存知识目录和数据库数据，不要随意使用 `down -v`。

首次初始化后更改 `.env.rag` 的根密码不会自动修改数据库里已存在的账户密码，需通过 Milvus 官方改密流程处理。

## 4. 没有本地 Docker 时

可先保持基础网页运行，或者由维护者提供已启用认证的远程 Milvus/Zilliz。不要把未启用认证的数据库端口直接开放公网。

如使用本机 API，把 `.env.rag` 中 `STUDYLENS_DATA_DIR` 改为 `var/knowledge`，`MILVUS_URI`、`MILVUS_TOKEN` 改为实际地址与凭据，然后执行：

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-rag.txt
.\.venv\Scripts\python.exe -m uvicorn studylens.api:app --env-file .env.rag --host 127.0.0.1 --port 8000 --workers 1 --no-access-log --limit-concurrency 16
```

另开一个终端，进入同一仓库：

```powershell
$env:STUDYLENS_API_URL='http://127.0.0.1:8000'
.\.venv\Scripts\python.exe -m streamlit run app.py
```

务必保持 `--workers 1`。版本目录和服务任务锁按单进程设计，多worker会破坏当前并发假设。图片识别仍需要操作系统的 Tesseract 和中英语言包。

## 5. 公网 HTTPS 与现有 Streamlit 网页

完整服务器部署可使用 `deploy/compose.public.yml` 中的 Caddy。先把网页与 API 两个域名解析到服务器，开放80/443，填写 `STUDYLENS_DOMAIN`、`STUDYLENS_API_DOMAIN` 后运行：

```powershell
docker compose --env-file .env.rag -f deploy/compose.yml -f deploy/compose.public.yml up -d --build
```

证书能否签发取决于域名解析、防火墙和服务器可达性。不要用公开 HTTP 传访问凭据。

如果继续使用 Streamlit Community Cloud 网页，在该应用的 Secrets 中增加顶层配置：

```toml
STUDYLENS_API_URL = "https://你的知识库API域名"
```

保存并重启应用。Cloud 只需基础 `requirements.txt`，它把知识库请求转发到独立服务。管理员和读者在页面输入自己的访问凭据；不要把服务器管理密钥写进 GitHub 或客户端源码。

## 6. 更新资料与接口行为

每份资料有稳定编号，例如 `polar-notes`。第一次导入创建资料；使用同一编号上传修改版会替换旧版；完全相同内容与元数据则返回未变化。上传后看提取警告，部分PDF导入可能不完整。

服务提供 `/v1/documents`（列表）、`PUT /v1/documents/{编号}`（原始文件体与filename参数）、`DELETE /v1/documents/{编号}`（删除）、`POST /v1/query`（问题与发送确认）。除 `/health` 外业务入口需要 Bearer 凭据。读者不能写入。更新接口要求 `X-External-Processing: true`，问答要求 `consent_external: true`。

资料准备、向量写入完成后才发布新版，失败不会把半成品混入活动版本。删除先撤销可见性，再做物理清理；返回 `cleanup_pending` 大于0表示还有清理任务，后续更新/删除会重试。仅传了文件并不代表服务已经成功发布，应查看返回结果和资料列表。

本版本没有自动监听电脑文件夹。外部业务系统应在文档变化时调用同一编号的更新接口，才能实现及时同步。

## 7. 故障定位

- 401：访问凭据错误；403：读者试图管理资料。
- 408：请求体上传超时；413：文件或请求过大；422：内容或编号不合法。
- 429：请求速度超限或上一任务仍在处理；按提示等待，不能无限自动重试。
- 503：配置、数据库、模型或处理流程暂不可用。先刷新资料列表核对状态，不能假定失败前一定没有提交。
- Agent 返回资料不足、澄清问题或错误记录：不是HTTP服务必然故障，可能是证据不足、模型输出不合约定、版本变化或预算耗尽。

`/health` 只表示服务进程活着，不检查付费模型。`/v1/status` 需要凭据，检查目录可读、Milvus集合可达并返回任务计数，不能当作真实模型质量验证。日志记录请求编号、方法、状态、耗时和异常类型，不记录原始问答或Key；转发代理也不要记录Authorization和请求体。

查看日志：

```powershell
docker compose --env-file .env.rag -f deploy/compose.yml logs --tail=100 api milvus
```

问答有次数、阶段时间和上下文上限，每个外部请求有超时。已到达服务商的请求不能靠浏览器关闭撤销费用。当前采用串行知识任务，适合小规模验证；没有完成并发容量与可用性SLA验收。

## 8. 备份、迁移和回滚

同时备份知识目录与 Milvus/MinIO/etcd 数据卷，并保留原始资料。只备份向量或只备份 SQLite 都不能完整恢复。

单节点可先停止服务写入，停止相关容器，再使用宿主机卷快照/备份工具保存一致时间点。恢复到隔离实例，检查资料数量、版本、可检索性、删除状态和访问权限后再切换。备份中可能含私密资料，应限制访问与保留时间。当前没有宣称已经做过你的生产恢复演练。

更换Embedding模型、维度或分块策略时，用新数据目录和新集合完整重建，经验证后切换。系统会拒绝在旧目录混用不同配置，不应删掉配置校验来强行启动。

基础修复回滚点是 `d687708`。大改有独立提交，发生问题可在保留资料备份后对升级提交执行 `git revert`，随后推送并重新部署。旧基础网页不读取新版知识库；回滚代码不等于回滚数据库版本。不要强推覆盖他人提交，也不要为回滚删除持久卷。

## 9. 正式使用前的验收

用真实但可公开的资料验证：导入 → 查询 → 修改 → 再查询 → 删除 → 确认不可查；测试只读凭据不能写入、重启后资料仍在、错误提示可恢复。再在独立评测集合中运行真实模型评测，人工核对答案与引用。

在没有这些结果之前，可以描述已实现的工程机制，不能写“生产零幻觉”“高并发稳定”或尚未实测的准确率。
